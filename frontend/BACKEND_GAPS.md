# Backend gaps

Original gaps from the first pass are resolved. This file now tracks what's left.

## Resolved

- **`GET /conversations`** — now returns each conversation with its member list (id + username) and last message. `useConversations` (`src/hooks/useConversations.ts`) replaced the old `localStorage`-backed `knownConversationsStore`.
- **User lookup/search** — `GET /users?q=` (search) and `GET /users/{id}` (lookup) now exist. `NewConversationDialog` searches real users instead of asking for a raw UUID; `directoryStore` and the old dev-tools UUID entry are gone.
- **Registration didn't establish a session** — `POST /users` now logs the new account in immediately (same session-cookie flow as `POST /login`), backed by a shared `internal/session` package.
- **Presence for a newly-added peer** — connecting now also receives a `presence.snapshot` event listing which of your peers are already online, in addition to the live `user.online`/`user.offline` push. This alone only helped once someone reconnected, though: two users already connected when they became conversation members (the common case — start a new chat, both already logged in) would never learn about each other at all, since nothing re-evaluates presence on membership change. Fixed properly: `POST /conversations/{id}/members` now calls `conversations.MembershipNotifier.NotifyMembershipAdded` (implemented by `realtime.Handler`), which sends the new member a presence snapshot of the conversation's other members and tells those members the new member is online, if they are — both directions, immediately, no reconnect required.
- **Picture and video attachments** — `POST /conversations/{id}/messages/media` generalizes the voice-message upload path (`internal/messages`) to `image/png|jpeg|webp|gif` and `video/webm|mp4`, capped at 8MB/50MB respectively with a 2-minute video duration cap enforced client-side. Images get a lightbox, video an inline player (`MediaAttachment.tsx`). Client-side canvas resize (`lib/image.ts`) keeps image payloads sane before upload.
- **Profile pictures** — a new `user_avatars` table plus `POST /me/avatar` / `GET /users/{id}/avatar` / `DELETE /me/avatar`, mirroring the voice-message attachment pattern exactly (same nosniff/CSP headers, same allowlist approach). `Avatar.tsx` falls back to generated initials when a user has none.
- **Unread badges / last-read tracking** — `GET /conversations` now includes `unread_count` per conversation, computed from the existing `message_receipts` table (messages from someone else with no receipt from you) — no new schema needed. The conversation list bolds unread rows and shows a count badge; an `@`-styled badge instead when the unread last message mentions your username.
- **TURN server** — `docker-compose.yml` ships a local `coturn` instance behind the `turn` Compose profile (`docker compose --profile turn up -d`; plain `docker compose up`/`./dev.sh` never pulls or starts it); `src/calls/peerConnection.ts` reads `VITE_TURN_URL`/`VITE_TURN_USERNAME`/`VITE_TURN_CREDENTIAL` and adds a TURN server to the ICE list on top of the existing public STUN server when configured.
- **Message reactions** — a fixed six-emoji palette (👍❤️😂😮😢🎉) stored in `message_reactions`, broadcast as `message.reaction_added`/`message.reaction_removed` over the existing realtime channel. Deliberately a fixed palette rather than free-text emoji, sidestepping grapheme-cluster validation entirely.
- **@mentions + highlighting** — client-side only: `MessageContent.tsx` highlights `@username` tokens that match a known conversation member, no schema change (mentions aren't resolved/stored server-side, so there's no dedicated "you were mentioned" notification beyond the conversation-list `@` badge, which is a same-page heuristic over the last message's text).
- **Markdown-lite formatting** — bold/italic/inline-code/auto-linked URLs, rendered client-side only (`MessageContent.tsx`) via a small hand-rolled tokenizer, not a markdown library — a rendering concern, no schema change.
- **Rate limiting** — a Redis-backed fixed-window limiter (`internal/ratelimit`) now throttles login attempts, account registration, and message/attachment sends per user or source IP.
- **Deafen** — distinct from mute: `useCallStore.isDeafened` mutes the local `<audio>` sinks in `CallAudioSinks.tsx` without touching the outgoing mic track, toggled via `callManager.toggleDeafen()`.
- **PWA installability** — `public/manifest.webmanifest` + `public/sw.js` (stale-while-revalidate for the app shell's static assets, network-first with shell fallback for navigations, complete passthrough for API/WebSocket paths so auth/session behavior is untouched). Registered only in production builds so it doesn't fight Vite's dev-server HMR.
- **Servers, not just groups** — the biggest structural item on the roadmap. A `servers` table owns named `server_channels` (text or voice), each backed by an ordinary group `conversation` row so messages/reactions/read-receipts/mesh-voice all work completely unchanged; `server_members` tracks membership separately from any one channel. Any member can invite (reusing the existing username-search flow) or leave; server channels are deliberately excluded from `GET /conversations` (see the `NOT EXISTS (... server_channels ...)` clause in `ListForUser`) so they don't show up twice. New leftmost "server rail" (`ServerRail.tsx`) switches between the DM view and each server's channel list, and a right-hand online/offline members panel (`ServerMembersSidebar.tsx`, `lg:` breakpoint and up) is the *only* place per-member presence shows — the left channel sidebar shows no other member's online status, only the signed-in user's own row (`CurrentUserRow`) at the bottom. No channel categories/reordering and no per-channel unread badges yet.
- **Localized (per-server) RBAC** — `server_roles` gives each server its own named, colored roles with five permission flags (`is_admin`, `can_manage_server/roles/channels`, `can_kick_members`); every non-owner member has exactly one role via `server_members.role_id`, defaulting to an auto-created "Member" role with no permissions. The owner isn't a role row — they always have every permission. `is_admin` is a blanket override ("grants everything regardless of its other flags"), matching the "admin toggle" ask. `GET /servers` and `GET /servers/{id}` return the caller's *effective* `permissions` alongside the full `roles`/`members` lists so the frontend never has to re-derive them. Known simplification: no role hierarchy/privilege-escalation guard — anyone with `manage_roles` (or admin) can grant any permission, including admin, to any role.
- **Server settings page** (`/servers/:id/settings`, gated on having any management permission) — Overview (rename, icon, banner), Roles (create/edit/delete, toggle permissions), Members (assign role, kick) — each section only rendered if the caller's permissions actually allow that action.
- **Clickable member profiles** — `MemberProfileModal.tsx` is a small, non-modal-feeling `<dialog>` (click outside or Escape to close) showing role, "joined `<server>`" and "joined bu3li comms" (month/year), the latter newly exposed via `users.created_at` on `User`/`GetByID`/`Search`/`/login`.
- **Server icons and banners** — `server_icons`/`server_banners` tables, same bytea-attachment pattern as avatars/voice messages (nosniff/CSP headers, allowlist). Icon shows in the server rail (falls back to initials) and settings; banner shows atop the channel sidebar and in settings.

## Remaining, by design

- **Voice call mesh doesn't scale past a handful of people.** Calls are peer-to-peer (each participant opens a direct `RTCPeerConnection` to every other participant) — fine for a direct call or a small voice channel, but bandwidth/CPU cost grows O(n²). A real "voice channel" product would need an SFU (e.g. mediasoup, LiveKit, Janus) mixing/forwarding media server-side. Out of scope here.
- **Calls aren't persisted.** `internal/realtime/calls.go`'s `CallRegistry` is in-memory only — a server restart drops active calls, and there's no call history/log. Reasonable for a demo; a real product would want at least a `call_sessions` table for history and reconnection support.
- **Voice/picture/video messages and avatars are stored as `bytea` in Postgres**, not object storage. Fine for a demo; a production system would put them in S3/R2/etc. and store a reference instead of streaming bytes through the app server on every playback.
- **No group-conversation membership UI beyond creation.** You can create a group and add members via the dialog, but there's no "manage members" screen after the fact.
- **No "servers" concept, no SFU voice, no end-to-end encryption, no federation.** All still exactly as speculative as ROADMAP.md describes them — none of this session's work touches those.
